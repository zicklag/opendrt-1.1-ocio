## Goal

Install the OpenDRT picture formation / output transform so it can be picked in
your Blender flatpak, alongside the bundled AgX, Filmic, ACES 1.3/2.0 views.

## What is built

- **Fetch pipeline** (`scripts/10-fetch-artifacts.sh`): pinned downloads of
  jedypod's OpenDRT v1.0.0 and v1.1.0 DCTLs, jedypod's v1.0.0 reference config
  zip, gripeyes' independent 64pt Standard cubes, ociogen source, and Blender
  5.2's bundled colormanagement directory.
- **Baker** (`scripts/20-bake-luts.py`): preprocesses the official DCTL into a
  standalone C++ bake executable, feeds it a T-LogE lattice (pre-decoded via
  the spi1d), writes `.cube` LUTs.
- **Config builder** (`scripts/30-build-config.py`): stages Blender 5.2's own
  config and splices in OpenDRT colorspaces and views plus the baked cubes.
- **Validator** (`scripts/40-validate.py`): fidelity gates, config checks,
  spot values, neutral-axis checks, check images.
- Deliverable folder: `dist/OpenDRT-1.1-Blender5.2` with `config.ocio`,
  `luts/opendrt/*.cube` (7 looks), and the T-LogE spi1d.

## Bug #1 — found and fixed

My spliced E-Gamut 2 matrix was packed as 9 gamut values followed by zeros.
OCIO reads a matrix as a row-major 4×4 with the affine term in the **4th
column of each row** (`m00 m01 m02 0 | m10 m11 m12 0 | …`). With the wrong
packing, OCIO misread a gamut value as the x-translation, which poisoned every
chain and produced the original green cast. Fixed with an interleaved packing
helper in the generator; revalidated; greys neutral in OCIO 2.6.

## What gripeyes' config — confirmed working in your Blender — does differently

Their wiring (config-acescg-ocio2.4.ocio):

- OpenDRT views are **plain colorspaces** whose from-scene chain is exactly
  `[CST(ACES2065-1 → T-LogE), FileTransform(cube)]`. The cube is the complete
  display transform, display encoding included; nothing runs after it.
- The T-LogE shaper colorspace defines **only** `to_scene_reference`; OCIO
  inverts it where the view chain needs the from-scene direction.
- The ACES→XYZ leg is `BuiltinTransform("UTILITY - ACES-AP0_to_CIE-XYZ-D65_BFD")`
  followed by the plain ociogen gamut matrix (7-digit values).
- Cubes are baked **per display encoding** (srgb-display, display-p3,
  rec1886), at 64pt.
- Config declared `ocio_profile_version: 2.4`.

Mine (the suspect pattern):

- OpenDRT wired as view_transforms ending in an extra XYZ-interchange CST plus
  per-display conversion hops (the display colorspaces did the final encoding).
- The ACES→XYZ leg via an aliased ColorSpaceTransform plus a diagonal
  white-point frame conversion. Mathematically fine in OCIO 2.6 (my composed
  matrix matched Blender's own E-Gamut matrix to 4.5e-8), but it is a
  structure gripeyes' proven config does not use.
- The shaper colorspace declares an explicit from-scene chain with the spi1d
  used in the inverse direction.
- 48pt cubes covering only rec1886 + PQ; relied on the display hop for sRGB,
  P3, and 2020.
- Config declared `ocio_profile_version: 2.5`.

## Decision

Adopt gripeyes' exact wiring pattern for my OpenDRT additions, keeping my own
DCTL-baked cubes so all 7 official looks (Standard, Arriba, Sylvan, Colorful,
Aery, Dystopic, Umbra) work:

- Rebake: five display encodings (`srgb`, `displayp3`, `rec1886`,
  `rec2100pq` @ 1000 nits, `rec2100hlg`) × 7 looks, at 64pt to match
  gripeyes' fidelity.
- The DCTL's srgb/displayp3 presets are pure 2.2-power encodings; Blender's
  sRGB/P3 display colorspaces use the piecewise sRGB curve. They agree closely
  except in deep shadows; rec1886 matches exactly. The Rec.2020 display is
  skipped — the DCTL has no Rec.2020-primaries SDR preset.
- Verified already: gripeyes' composed leg (BFD builtin + their matrix) maps
  ACES white → E-Gamut2 white exactly in OCIO 2.6 (white (1,1,1) → (1,1,1),
  greys invariant, primaries stay unit vectors).
